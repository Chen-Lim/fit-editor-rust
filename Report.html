3. Critical findings

C1CRITICAL  Box::leak 永久泄漏

Verdict: 阻塞合并。这是 Rust 程序员入门第二章就应当避免的事。
Fixed in 0de9c45 — SDK Value::Enum changed to String; CLI Box::leak removed

两处现场:

// src/commands/edit.rs:167
Value::Enum(_) => Value::Enum(Box::leak(s.to_string().into_boxed_str())),

// src/commands/encode.rs:123
Value::Enum(Box::leak(s.clone().into_boxed_str()))

每次解析 JSON 中的 enum 字段、每次执行 --set 编辑 enum 字段， 都把一份 String 的堆缓冲泄漏成 &'static str。这些内存到进程退出都不会归还。

在 batch 命令处理 1000 个文件、每个文件包含 sport/event/event_type 等典型 enum 字段几百次的场景下，泄漏量进入 10–100 MB 量级。 用户跑 fit-editor batch '*.fit' -- fit-editor edit --set 'session.sport=running' 时不会得到任何提示。

根因是上游 fit::Value::Enum(&'static str) 的 API 设计本身有问题 —— 把 lifetime 推到消费者头上，逼着消费者要么 leak、要么自建 interner。 本仓库与 fit-sdk-rust 是同一开发者维护的 path dep（见 Cargo.toml:18）， 所以正确的修复是改 SDK，把 Value::Enum 改成 Arc<str>、Cow<'static, str>，或者直接 String。 在 CLI 层用 Box::leak 兜底，是把 API 缺陷传染到所有下游应用。

Required fix: 修 fit-sdk-rust 的 Value::Enum 表达，CLI 同步迁移。不接受 "TODO 以后再说"。

C2CRITICAL  GPX 导出制造 "Null Island" 幽灵轨迹

Verdict: 阻塞合并。这是 silent data corruption，不是排版问题。
Fixed in 0de9c45 — GPX exporter now skips records without GPS coordinates

原文 (src/commands/export.rs:205–216):

let has_coords = lat.is_some() && lon.is_some();
let lat = lat.unwrap_or(0.0);
let lon = lon.unwrap_or(0.0);

if !has_coords && ele.is_none() && time.is_none() {
    continue;
}

gpx.push_str(&format!(
    "      <trkpt lat=\"{:.7}\" lon=\"{:.7}\">\n",
    lat, lon
));

含义：当一条 record 没有 GPS 坐标，但 有 ele 或 time 时， !has_coords && ele.is_none() && time.is_none() 为 false，逻辑继续走， 输出 <trkpt lat="0.0000000" lon="0.0000000">。

室内活动 —— 跑步机、骑行台、游泳、瑜伽、举铁 —— 是 FIT 文件最常见的子集之一。它们没有 GPS，但每秒都有 timestamp 与心率。 把这些 record 写成坐标 (0, 0) 的轨迹点，等价于在赤道与本初子午线交点（几内亚湾外海）放一条假轨迹。 上传到 Strava 之后，用户会得到一条横跨大西洋的诡异 PR。

Required fix: 把判断改成 if !has_coords { continue; }。 需要保留 non-spatial 数据的话用 GPX <wpt> 或 TCX，不要在 trkseg 里制造假坐标。

顺带：这条逻辑没有任何测试覆盖。tests/phase2.rs 里 GPX 这个词出现 0 次。

C3CRITICAL  merge 命令产出非法 FIT

Verdict: 阻塞合并。功能描述与功能行为不一致。
Fixed in 0de9c45 — merge deduplicates metadata, uses as_datetime() for timestamp sort

问题一：多份 file_id。merge.rs:16–28 把 N 个文件的 messages 全部 extend 到一个 Vec，没有去重 metadata-only 消息（file_id、file_creator、device_info、developer_data_id、field_description 等）。FIT 规范要求一个文件只能有一个 file_id，且必须位于最前。当前实现产出的 .fit 在 Garmin Connect / Strava / fitparse 上行为不可预测。

问题二：排序键根本没生效。

// src/commands/merge.rs:53–55
fn extract_timestamp(msg: &Message) -> Option<u64> {
    msg.field("timestamp").and_then(|f| f.value.as_u64())
}

SDK 默认 Decoder 是 apply_scale_and_offset(true) + convert_datetime(true) （参见 dump.rs:25–32，需要显式关闭才会拿到 raw u64）。 也就是说，timestamp 字段在 merge 时是 Value::DateTime(DateTime<Utc>)。 Value::as_u64() 对 DateTime 返回 None —— 所有消息都被视作"无 timestamp"。

Option<u64>::cmp 把 None 排在 Some(_) 前。 所有消息时间戳都是 None ⇒ 比较结果全部相等 ⇒ sort_by 退化为稳定的"维持原顺序"。 也就是说，merge 命令实际上是按文件顺序 concat，不是按时间合并。 这与 cli.rs:117 的描述 "Merge multiple FIT files by timestamp" 直接矛盾。

Required fix:

  • (a) 用 match &f.value { Value::DateTime(dt) => Some(dt.timestamp()) , _ => None } 取真实 epoch 秒；
  • (b) 第一个文件保留全部 metadata-only 消息，后续文件丢弃其 file_id/file_creator 等；
  • (c) 在 merge 测试里加一条 "两个文件，第二个比第一个早，merge 后第一条 record 来自第二个文件" —— 这条测试现在不存在。

H1HIGH  hexdump 的越界 panic

Verdict: 不接受。诊断损坏文件的工具被损坏文件干掉。
Fixed in 0de9c45 — bounds check changed to data.len() < 6
// src/commands/hexdump.rs:122–129
fn estimate_definition_size(data: &[u8]) -> usize {
    if data.len() < 5 {
        return data.len();
    }

    let has_dev_data = (data[0] & 0x20) != 0;
    let field_count = data[5] as usize;  // <-- panic when data.len() == 5

边界条件少了 1。data[5] 要求 data.len() ≥ 6，而检查只到 < 5。 用户的典型用例就是 fit-editor hexdump --annotate broken.fit，恰好在 truncate 处崩溃，把诊断工具变成共犯。

Required fix: if data.len() < 6 { return data.len(); }。 后面 data[size] 的访问也需要复核 —— 那块用了 size < data.len() 守卫，看起来 OK，但越界检查应当统一抽出 helper，而不是每处再人肉证明一遍。

H2HIGH  validate 对 decoder 错误失明

Verdict: 不接受。validate 一词被滥用，CLI 在对用户撒谎。
Fixed in 0de9c45 — validate now calls Decoder::read_all(), reports decoder errors with exit code 2
// src/commands/validate.rs:7–27 — 全文
match fit::check_integrity(&bytes) {
    Ok(()) => println!("{}: {}", file.green().bold(), "valid".green()),
    Err(e) => eprintln!("..."),
}

check_integrity 只看 CRC + 签名 + 文件长度。它不解码消息。 其他每个命令都做 let (msgs, _errors) = Decoder::builder(&bytes).build().read_all();， 然后把 _errors 静默丢弃（info.rs 和 dump.rs 仅在 --verbose 才打印）。

后果：一个 CRC 正确但解码层有问题（未知 global mesg num、definition 与 data 不匹配、字段类型异常）的文件 会被 validate 显示为绿色 "valid"，紧接着 dump 出来一半消息丢失。

Required fix:

  • validate 必须跑 read_all 并报告 errors.len()。
  • --verbose 下打印每条 decoder error。
  • exit code 在 errors 非空时返回 2（与硬错误 1 区分）。

H4HIGH  无文件大小上限

Verdict: 不接受。一个 CLI 工具如果上 CI / 服务后端无法生存，0.1.0 不能这样发。
Fixed in 0de9c45 — read_bounded() helper added, 256 MiB default limit on all fs::read calls

所有 12 个命令的入口都是 let bytes = std::fs::read(path)?; —— 一次性把整个文件读进 Vec<u8>。 encode 同理（fs::read_to_string）。merge 把 N 份 Vec<u8> 同时常驻、外加合并后的 messages， 内存放大约 3×。

桌面手动跑时无所谓，因为用户不会自己 DoS 自己。 但是 README 明确把 batch 命令作为卖点，而 batch 接受 glob —— 一个 10 GB 的 .fit 或者一组 1000 × 100 MB 的 .fit 就足以让进程 OOM。

Required fix:

  • 读 header 后用 header.total_file_size() 与一个上限（建议默认 256 MB，--max-file-size 可覆盖）比较。
  • 长期方案：迁移到流式 decoder（BufReader<File> + 增量解码），不要再把整个文件读进内存。

M1MEDIUM  .unwrap() on progress template

// src/commands/batch.rs:30–34
ProgressStyle::with_template("[{bar:40.cyan/blue}] {pos}/{len} {wide_msg}")
    .unwrap()

模板字符串虽然是编译期常量，.unwrap() 仍然是显式的 "我相信不会失败" 声明， 但当前写法没有把这个 invariant 写出来。最低限度改成 .expect("progress template is valid")， 让下一个动这块代码的人知道自己在打破什么。

M2MEDIUM  unreachable!() 在主循环里

// src/commands/diff.rs:37–68
let max_len = filtered1.len().max(filtered2.len());
for i in 0..max_len {
    match (filtered1.get(i), filtered2.get(i)) {
        (Some(a), Some(b)) => { ... },
        (Some(a), None) => { ... },
        (None, Some(b)) => { ... },
        (None, None) => unreachable!(),  // "this can't happen"
    }
}

数学上 (None, None) 确实不可达。但控制流结构让编译器无法证明这点， 所以 unreachable!() 必须运行时检查。下一个改 loop 边界的人（比如想用 max(filtered1.len(), filtered2.len()) + 1 来包含 trailing sentinel）会立刻引爆。

正确写法用 itertools::zip_longest:

use itertools::{Itertools, EitherOrBoth};
for (i, pair) in filtered1.iter().zip_longest(filtered2.iter()).enumerate() {
    match pair {
        EitherOrBoth::Both(a, b) => { ... }
        EitherOrBoth::Left(a)    => { ... }
        EitherOrBoth::Right(b)   => { ... }
    }
}

类型系统证明三分支穷尽，unreachable!() 消失。

M3MEDIUM  JSON number → 整数静默截断

// src/commands/encode.rs:97–112
serde_json::Value::Number(n) => {
    let f = n.as_f64().unwrap_or(0.0);
    ...
    match fi.type_name {
        "uint8" | ... | "uint64" | "uint64z" => Value::UInt(f as u64),
        "sint8" | ... | "sint64"             => Value::SInt(f as i64),
        "float32" | "float64"                 => Value::Float(f),
        _                                     => Value::Float(f),
    }
}

两层静默改值：

  • n.as_f64().unwrap_or(0.0) —— 超出 f64 表示范围（不存在）或者 arbitrary_precision 编译特性下失败时静默变 0； u64 超过 253 的精度损失永远不报。
  • f as u64 / f as i64 —— Rust 1.45+ 是饱和转换，不 panic，但对 NaN 给 0，对超界给 {u,i}{64}::MAX/MIN。 用户手写 JSON 想 round-trip 一个 u32 时间戳，写错成 1e20 之后会被悄悄改成 u64::MAX， encoder 不会报错，validate 也通过，没有任何反馈机制。

Required fix: 优先 n.as_u64() / n.as_i64()；只有这两个返回 None 才退回 as_f64 + 范围检查；超界返回错误而不是 Value::Invalid，因为 Value::Invalid 在 round-trip 里语义不同（"字段不存在"）。

M4MEDIUM  batch 用 process::exit(1) 跳过 error 流

7. Architectural notes

不是直接 bug，但合并前值得讨论：

  • SDK API 把 lifetime 推给消费者。Value::Enum(&'static str) 是设计错误， 被本仓库用 Box::leak 兜底（C1）。SDK 是同一 author 的 path dep，所以这是可以并且应该一起改的。 推荐 Value::Enum(Arc<str>)；profile 表里的静态字符串用 Arc::from(&'static str) 是常数时间的封装。
  • Decoder 错误是 silent 的。每个 callsite 都 let (msgs, _errors) = ...read_all();， 然后只在 --verbose 才有时打印。一个 maintainer 决定不是 callsite 决定。 Decoder::builder 应当支持 .strict()，让错误成为命令本身的错误，而不是悄悄少几条 message。
  • 没有 lib.rs 是这个仓库最大的工程错误。 把 cli / commands / error 拆到 src/lib.rs + 一个薄 src/main.rs， 获得：单元测试可达、doctests 可达、其他 crate（脚本工具、Tauri 桌面壳）可以直接复用。 工作量约半天。
  • 错误模型不连贯。CliError 有 7 个变体，但缺少 BadUsage、DecodeFailed、 OutputAlreadyExists 等业务变体；同时 UnknownMessage（error.rs:16）是 #[allow(dead_code)] —— 死变体不该留着。
  • "summary" 与 "info" 的边界模糊。两个命令都解析 header、都列 message 信息。 info 给出 header + message counts；summary 给出 session 派生统计。 名字与职责对得上，但 README 的描述里没把这一点讲清楚，新用户大概率不知道该选哪个。

8. What is actually fine

为了不显得只会喷，下面这些是这个仓库现在做对的事：

  • No unsafe code。rg unsafe src/ 零匹配。
  • 模块边界干净。main.rs 105 行纯路由，没有业务逻辑泥潭；每个 subcommand 一个文件， 改一个不会牵动另一个。这是这个仓库目前最大的优点。
  • 错误传播用 From + ? 而不是 anyhow 兜底。error.rs:74–91 的 From<fit::FitError> 把 SDK 错误映射到 CLI 错误，调用点保持干净。
  • CRC 错误信息带 hex 值（error.rs:41–44），调试时一眼定位。
  • TTY 检测与 --no-color（main.rs:13–16）； 进度条在非 TTY 自动隐藏（batch.rs:27–39）。 这层 UX 礼仪比大量新 CLI 强。
  • man pages 通过 clap_mangen 在 build.rs 里生成。0.1.0 阶段做这件事是认真的信号。
  • clippy 无 warning（开发者已确认）。这是基线，但比一堆 lint 噪音的仓库强。

上面这几条决定了我相信这个仓库可以在 2–3 周内被修到可合并的状态。如果模块边界本身一团乱，那不会。
